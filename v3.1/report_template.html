独立 buffer / barrier 池与阻塞 API

按任务在提交前依次 get/set buffer、get barrier，再 submit_async。API 资源不足时协程停在调用内，保留此前已取资源，其他 engine 和回收控制继续推进。

buffer ID 与物理 buffer 一一对应，拥有独立 free/flag 位图；barrier 池只计数据依赖和共享 buffer 的消费完成事件，不再分配 empty barrier。

达标资源边界

边界限于当前程序、申请顺序、队列深度、调度策略和扫描范围。增加资源可能改变提交节奏，因此不假设性能单调，也不把“最小 buffer”和“最小 barrier”分别拼成未经验证的组合。

实际流水、buffer 与 barrier 生命周期

Buffer：从 get 开始占用，直到 free_buffer

浅色：预分配及整个存活区间蓝条：生产者计算绿条：消费者读取灰色：外部源输入

Barrier：从 get 开始占用，等待 SET 后消费回收

蓝色 D：数据依赖橙色 R：共享 buffer 消费完成事件实心上条：已 SET，尚未 WAIT

准确复现的协议
    

  • 一个全局前端按任务顺序申请资源；单次 get 不足时阻塞调用，已获得的其他资源保留，不回滚、不跳过当前任务。
    • 

  • buffer 和 barrier 使用同构但独立的位图事件池。get 清 free 位，set 置 flag；wait/free 要等 flag，再清 flag 并将 ID 放回对应 free-list。
    • 

  • set_buffer 表示本次资源占用初始化完成，不表示生产数据就绪；数据就绪由生产者完成时 set_barrier 表达。
    • 

  • 四种执行单元各一个，队列默认深度 5。submit_async 只入队；WAIT_ALL 在实际发射时消费 ID。同一 engine 不重叠执行。
    • 

  • vector1R2 输出有两个消费者：两个独立数据 ID，另有两个消费完成 ID。回收控制 WAIT_ALL 后只 free 一次共享 buffer，两个完成 ID 真实计入容量。
    • 

  • 回收控制在全部直接消费者提交后注册，独立于前端，不占用第五个计算 engine；本模型假定控制上下文无额外容量或服务延迟限制。
    • 

  • 首级 RDMA 的外部输入也占池内 buffer；末级结果完成即被外部接收。全部操作和回收控制排空后，两类 ID 都应全部空闲。
    • 

  • 所有 API 服务、回调和控制操作为零耗时；仅各计算块使用原图测量时长。它是容量和调度模型，不是真实数据计算或完整硬件面积模型。
    • 

运行命令与有效配置


v3.1 的资源分配时点和事件池结构与 v3 不同，不能直接套用旧版最小容量。旧版本及原有未提交文档均保持不变。
