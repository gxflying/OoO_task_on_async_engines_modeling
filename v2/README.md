# Modeling v2：共享 buffer 复用与最小容量

本版本位于 `modeling/v2`，不修改 v1。沿用原图像素时长、100 轮、每个执行队列深度 5、一个全局按程序序入队前端，以及 RDMA/WDMA/Tensor/Vector 各一个执行单元。

直接打开 [out/report.html](out/report.html)。报告包含 1～12 块容量扫描、OoO/FIFO 流水、每个物理槽位的复用时间线、生产者/消费者详情，以及完整复现 v1 的峰值证据。

## 已确认结论

| 目标 | 所需物理 buffer | 证据 |
|---|---:|---|
| 当前最老就绪优先调度下，维持 298 px/轮稳态吞吐 | **9 块** | 逐个扫描 1～12；1～8 均未达标；9 块在 100/300 轮均保持目标 |
| 完全保持 v1 每条指令的入队/开始/结束时刻 | **11 块** | v1 数据存活区间同时重叠峰值为 11；v2 11 块实际执行逐条匹配 |

若每块大小为 B，总池容量分别为 **9B / 11B**。没有假设未经提供的具体字节数。

这里的 9 块是**当前确定性调度和分配规则下**的最小达标数，不是对所有可能的调度算法作全局最优证明。11 块则是给定 v1 固定时序的区间重叠下界，且有可行分配轨迹，因此对该固定时序是精确值。

9 块时，一些 `load V` 和对应 WDMA 延后，例如第 3 轮 `load1R2` 从 v1 的 777 延后至 801；Tensor 和 Vector 的指令开始/结束时刻保持不变，100 轮总耗时仍为 **30097**。稳态 Vector 利用率 100%，没有等 buffer 的空闲。RDMA 每个周期多等待 24 px 的 buffer，但该等待落在非关键数据预取的余量内。

## 生命周期合同

用户明确确认：

- 有数据依赖时，上游输出就是下游输入，指向**同一块物理 buffer**，不做复制或重复计数。
- 两条依赖都对应数据输入，双输入指令执行时要保留两块输入。

具体模型规则：

1. 所有 buffer 大小相同，处于跨执行单元共享池。每条指令产生一个输出 buffer。
2. 普通指令直接读取其各生产者的输出，另分配一个输出槽；输出不能与任何输入同址，不允许原地覆盖。
3. 无上游的 RDMA 每次执行需要一个池内外部输入 buffer 和一个输出 buffer，二者原子分配。外部数据在发射时已就绪，不另计准备延迟。
4. 输出从**生产者开始执行**起占用，生产者完成只标记 ready；最后一个直接消费者**执行完成**后才释放。
5. 尚未发射的消费者同样持有引用，不能因为当前 active reader 为零而回收。fan-out 的全部消费者完成后才释放。
6. RDMA 外部输入在该次 RDMA 完成时释放。末级 `vector1R4/fa2` 没有内部消费者，其输出假定由外部 sink 在生产者完成时立即接收，此时释放。
7. 上述第 3/6 条是边界假设。若输入来自池外，或最终结果需长期保留，必须修改边界配置重新测试，不能直接套用 9 块结论。`count_source_inputs: false` 可用于前一种口径。
8. buffer 在指令**发射时**分配，入队不预占。所需新槽一次性分配成功才发射；不足时不改变状态，不半分配。
9. 时间边界先处理所有完成、释放，再入队、分配、发射。刚释放的槽可同一时刻复用，执行和生命周期都采用半开区间 `[start,end)`。
10. 物理 handle 为 `(slot,generation)`，每次复用递增 generation；旧 handle 无法读写新的 lease。所有消费者在开始读取时核对 handle、ready 与所属生产者。

同时分配的引擎仲裁顺序与 v1 相同：RDMA → WDMA → Tensor → Vector。OoO 在每个队列中选最老的“依赖完成且 buffer 足够”的指令；FIFO 只检查队首。有限 buffer 会改变可发射集合，因此增加 buffer 不保证此贪心策略的性能单调提高。

## 100 轮扫描结果

| buffer 数量 | 状态 | 总耗时 / px | 稳态平均间隔 / px | 达到 298 目标 |
|---:|---|---:|---:|---|
| 1 | 无法发射首条指令 | — | — | 否 |
| 2 | 中途资源死锁，0 轮完成 | — | — | 否 |
| 3 | 完成 | 79300 | 793 | 否 |
| 4 | 完成 | 65935 | 660 | 否 |
| 5 | 完成 | 58667 | 587 | 否 |
| 6 | 完成 | 59376 | 595 | 否 |
| 7 | 完成 | 44953 | 448.25 | 否 |
| 8 | 完成 | 47584 | 477 | 否 |
| **9** | **完成** | **30097** | **298** | **是** |
| 10 | 完成 | 30097 | 298 | 是 |
| **11** | **完成且完整复现 v1** | **30097** | **298** | **是** |
| 12 | 完成，实际峰值使用 11 块 | 30097 | 298 | 是 |

8 块在稳态窗口有 **17363 px 的 Vector 等 buffer 空闲**；9 块降为零。5→6、7→8 的退化已实测并保留，没有用二分或“容量越大必然越好”替代扫描。

9 块的稳态状态在 t=690、988、1286 重复；统计窗口 `[690,29596)` 包含 97 个周期，平均存活约 8.09 块，峰值 9 块。FIFO 使用同样 9 块时，本次为 390 px/轮、总耗时 39185；报告的顺序 tab 使用这条真实轨迹。

## 实现与验证

- `memory.py`：共享池、原子分配、read/write 生命周期、全消费者引用计数、版本化 handle、事件日志。
- `simulator.py`：真正把可用 buffer 加入发射条件；事件驱动推进到下一次执行完成，与 v1 的整数时间语义一致，不添加执行延迟。
- 完整状态稳态检测包含前端、队列、在途指令、完成 token、每个存活 buffer 的生产者、剩余消费者、当前读者和 ready 状态。由于所有物理槽无容量或 bank 差异，稳态比较允许物理槽位等价重命名，generation 不影响时序。
- 独立轨迹检查从 lease 区间重建输入来源和释放时间，检查输出不覆盖输入、一个槽上的不同代生命周期不重叠、最后消费者完成后释放、队列容量和执行单元不冲突。
- **15 项测试通过**：原子失败、提前释放保护、fan-out/late consumer、真实双输入、同引擎连续处理、同一时刻释放/复用、stale handle、生命周期损坏检测、全部容量扫描、300 轮复核；另有 24 个固定种子的随机 DAG 与 v1 的 OoO/FIFO 时序交叉比较。
- 浏览器检查已覆盖三个 tab、1000 条指令/1200 个 lease、方块坐标、时间游标、生命周期详情、11 块峰值定位、SVG 导出和 390px 窄屏。第一次检查发现峰值定位的 range 控件被旧范围钳位，已修复并通过复测。
- `baseline_manifest.json` 和 `out/verification.json` 验证 v1 核心代码、配置和既有报告数据的 SHA-256 保持不变。

没有执行矩阵运算、带宽仿真或真实 SRAM/DRAM 访问；本次实现的是物理存储槽的容量和所有权模型。该边界不影响对防覆盖和释放/复用时序的检查。
